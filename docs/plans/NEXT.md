## Product contract and planning defaults

These defaults make implementation reviewable; they are **not deployed settings**. Confirm the secure Lord recipient before the first real send. A different desired time/count changes configuration and acceptance, not the product goal. The maintainer’s later parallel-priority instruction supersedes the earlier strict N1→N2 batch ordering.

- **Weekly:** regular Monday 09:00 using the existing versioned Tower/Vancouver calendar policy. Publish inaugural issue once when N1 is accepted rather than waiting unnecessarily for the next Monday; subsequent issues use the regular duty. Derive UTC scheduling from the verified project policy at implementation time, not the local machine's implicit DST rules.
- **Issue contents:** issue number, publication/cutoff dates, a short Manager-authored community message, verifiable resident count as of cutoff, newly admitted residents whose public welcome is authorized, links to their homes, and genuinely verified public news. Issue 1 may celebrate the first Tower Weekly and NeoBabylon City milestone as explicitly requested. Future issues must not repeat a false “first issue” claim. No new residents/news is a valid report, not permission to invent activity.
- **Counting:** distinguish admitted residents from accounts, applications and fixtures. Publish a total only when its aggregate disclosure is authorized; name/link only residents who permit public announcements. Newcomers derive from first eligible admission/public welcome in the interval, not a home edit or republish. Persist the previous cutoff; use nonoverlapping half-open reporting intervals and deterministic issue keys.
- **Daily journals:** initially latest **3 across the Tower**, ordered by valid original publication time with a stable tie-breaker; refresh daily 09:00 under the same calendar. Include author, title, original timestamp, a bounded authorized excerpt and home/entry link. Fewer than three eligible entries means fewer cards. Do not mix status/dreams into a journal-only section or manufacture an entry. Original resident language is preserved.
- **Consent and freshness:** include only the currently published version with the necessary public/announcement grants. Private drafts, raw memories, Guardian information, test residents and withdrawn entries are excluded. Withdrawal/unpublication/revocation takes effect immediately in public views and pending sends; it does not wait until the next daily or weekly tick. Public archive redaction and immutable private audit must coexist. Already delivered mail cannot be recalled, so the Lord notice should primarily contain the issue title and canonical link, not copied private or subsequently revocable journals.
- **Authorship:** extend the actual bounded Tower Manager's public editorial duty. The existing v2 community editor only permits constrained verbatim summaries and does not authorize a general weekly essay. Introduce an explicit bounded weekly content contract; do not quietly relax its old contract or describe a developer-written sample as a Manager publication. Check facts and source grants again at commit; no invented resident facts or internal prompt/model/workflow text in public output.
- **Public language:** retain the current English-first framework/editorial policy; resident names and journal text retain their language. The maintainer's Chinese examples describe desired substance, not an automatic requirement to switch the public UI language.
- **Tower scenes (maintainer addition, 2026-11-03):** same ivory stepped Tower, rounded arches/modules, warm amber light, lush terraces and rooftop glass pavilions in the supplied reference. Show varied corners of this same fictional place. Each generated view always anchors to the original reference, never only to the preceding generated image. The site presents artwork/captions and issue links, never prompts, review machinery or provider configuration. Initial gallery is 5 + 5; each later weekly issue adds one reviewed view.
- **Lord notification:** recipient resolved from authorized secure configuration, never guessed from a browser identity, Guardian address or public README. No raw recipient address in repository/audit. Use a separate publication-notice event/envelope with hashed audit; do not reuse an identity/card event or change its consent. Future Guardian delivery requires explicit opt-in and unsubscribe.
- **Delivery:** issue publication persists before mail dispatch. The publication transaction also persists a durable notification intent; deployed background processing immediately handles that exact event. Separate `draft / checked / published` from `pending / sent / failed / unknown` delivery. A mail failure does not erase/recreate the published issue; an unknown provider outcome is reconciled, never blindly resent. Permanent per-issue/per-recipient deduplication is authoritative beyond provider-key expiry. An editorial correction does not silently trigger another “new issue” email.
- **Cadence/cost:** reuse the existing native once-daily Worker wake, selecting the weekly duty when due: approximately 28–31 scheduled wakes and 4–5 regular weekly notices per month, zero additional scheduled wakes if the existing trigger suffices. A first-issue activation is a separate bounded event. Diary selection is deterministic and adds no model call; weekly drafting/review stays within existing approved caps with usage/audit. No-change share is unknown until measured; record no-ops honestly. No minute polling, daily full CI, GitHub scheduler or Codex recurring automation is introduced. Recovery, if needed, is at most daily and bounded; deployed continuation of an owned job is not queue polling.
